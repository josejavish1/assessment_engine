### Perspective 2: The SOTA Compute & Virtualization Fellow (Technical Purity)
* **VMware vSphere Admission Control & 2-Node HCI Mathematics:** The deliverable states that 6 SimpliVity nodes are structured into **3 clusters of 2 hosts each** across two CPDs, operating at **95% physical RAM utilization**, eliminating the 50% buffer required for failover. Let us dissect the hypervisor physics omitted by the authors:
  1. **Admission Control Failure Domain Math:** In a 2-node cluster ($N=2$) with Host Failures Cluster Tolerates ($FTT=1$), the required cluster-wide resource reservation is strictly $\frac{N-1}{N} = \mathbf{50\%}$. If physical RAM utilization is at 95% across both hosts in a 2-node cluster, **vSphere HA Admission Control is either disabled (`EnforceAdmissionControl = False`) or severely violated.**
  2. **The HPE SimpliVity OVC Memory Trap:** On HPE SimpliVity 380 nodes (circa 2018), the **OmniStack Virtual Controller (OVC)** is a mandatory infrastructure VM pinned to each ESXi host that consumes between **32 GB and 96+ GB of non-pageable, 100% locked physical RAM** (`sched.mem.pin = "TRUE"`) to manage the inline deduplication/compression Accelerator card (or software stack) and the SimpliVity Distributed File System (SVTFS). This reduces usable host memory *before a single guest VM boots*.
  3. **Hypervisor Swap & SVTFS Starvation Cascade:** If CPD-1 loses power (as happens during cement kiln/mill electrical surges) and vSphere HA attempts to restart VMs on the surviving host in CPD-2 at 95% baseline load, total memory demand approaches **190% of physical RAM**. The ESXi kernel (`vmkernel`) will immediately transition through `High` $\rightarrow$ `Clear` $\rightarrow$ `Soft` $\rightarrow$ `Hard` $\rightarrow$ `Low` memory states:
     * `vmmemctl` (balloon driver) will inflate to its maximum cap across guest OSs (causing Oracle 10g/11g SGA paging inside guest Linux/Windows VMs).
     * Hypervisor-level memory compression and **host swapping (`.vswp`)** will trigger.
     * Because the `.vswp` files reside on the **SimpliVity SVTFS datastore**, and SVTFS I/O is processed by the OVC, massive swap storms saturate the OVC's vCPU queues and storage I/O path, inducing **APD (All Paths Down)** or **PDL (Permanent Device Loss)** SCSI timeouts across *all* surviving VMs.
* **S3 vs. Block/File Persistence for Kubernetes (CSI Fallacy):** In P2, the report praises the provisioning of **NetApp S3 object storage** so developers can *"consumir almacenamiento persistente para sus primeras cargas contenedorizadas."* **This is a classic architectural antipattern.** Kubernetes `PersistentVolumeClaims` (PVCs) for stateful workloads (databases, message queues, legacy state) require **POSIX file (`ReadWriteMany` via NFS) or Block (`ReadWriteOnce` via iSCSI/NVMe-oF)** provisioned dynamically via **NetApp Astra Trident CSI**. S3 is an HTTP/REST API object store consumed at the application layer via SDKs, not a primary POSIX mount for standard K8s stateful pods (unless wrapped in FUSE drivers like `s3fs`/Mountpoint, which breaks POSIX locking semantics).

### Perspective 2: The SOTA Compute & Virtualization Fellow (Technical Purity)
* **Kernel & Hypervisor Vulnerability Exposure (613 Days Uptime):** 613 days of continuous ESXi uptime places the patch level back to at least **mid-2024 or earlier**. This exposes the management plane and `vmkernel` to catastrophic, actively exploited hypervisor escape and ransomware vectors (e.g., **CVE-2024-37085** Active Directory ESXi admin group hijacking used by Akira/Black Basta, and **CVE-2025-22224 / CVE-2025-22225 / CVE-2025-22226** TOCTOU & VMCI heap-overflow hypervisor escapes allowing an attacker inside a compromised CentOS 5/6 guest to execute arbitrary code directly in the ESXi `vmx` process).
* **Linux Kernel Obsolescence (CentOS 5 / 6):**
  * **CentOS 5** (Kernel `2.6.18`, EOL March 2017) and **CentOS 6** (Kernel `2.6.32`, EOL November 2020) lack **cgroups v2**, modern paravirtualized drivers (`vmxnet3` / `pvscsi` modern ring buffer optimizations), and modern TLS 1.2/1.3 cipher suites (`OpenSSL 0.9.8e / 1.0.1e`).
  * Running these guests on modern multi-socket Xeon architectures with 95% RAM pressure without strict **vNUMA (Virtual NUMA)** alignment causes severe remote-node memory access latencies when `vmkernel` splits a monolithic Oracle 10g/11g VM across physical NUMA nodes.

A **Strangler Fig pattern** via an API Gateway / Event Mesh (CDC via Debezium/GoldenGate out of Oracle into modern services) coupled with **KubeVirt** or a modern hypervisor refresh is required—not lift-and-shift containerization.
